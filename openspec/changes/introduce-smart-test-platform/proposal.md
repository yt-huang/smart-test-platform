# Proposal: introduce-smart-test-platform

## Why（为什么做）

公司当前测试处于 L0（脚本级自动化）状态：各项目各自维护脚本、无统一框架、无资产沉淀、无资源池，回归依赖人工与零散自动化，缺陷逃逸率与回归耗时不可度量。市场侧，AI 测试行业正以 18%+ 的 CAGR 增长，"自动化→智能化"已成行业主线；技术侧，Playwright/Appium/Midscene 等开源骨架与优测/WeTest 等商业云真机已成熟，引入窗口期良好。不引入统一平台的代价是：每次发版的回归成本线性增长、机型兼容问题依赖线上反馈、测试资产随人员流动流失。

## What（做什么）

引入一套覆盖 **手机端（Android/iOS/鸿蒙/小程序）与 Web 端** 的智能测试平台，分四个阶段：

- **P0 诊断与基线（M0–M1）**：盘点现状，建立可度量基线（缺陷逃逸率、回归耗时、flaky 率），确定 Top 20 机型与浏览器矩阵。
- **P1 框架统一（M1–M3）**：Web 定版 Playwright、移动定版 Appium；浏览器容器池上线；CI 接入 PR 冒烟门禁；开通 1 个商业云真机账号跑通主链路。
- **P2 平台化（M3–M8）**：测试管理平台（MeterSphere）承载用例/计划/报告/缺陷闭环；自建 10–20 台核心机池（Sonic）与云真机统一调度；质量度量看板上线。
- **P3 智能化试点（M8–M12）**：Midscene + 私有化视觉模型在 2 条业务线试点 UI 自愈；大模型辅助生成接口/功能用例（人工审核入库）；失败智能归因与 flaky 自动隔离。

## 范围边界

- **包含**：Web/App UI 自动化、接口测试接入、兼容性矩阵、设备与浏览器资源池、测试管理与报告、CI 门禁、AI 用例生成/自愈/归因（试点）。
- **不包含**：性能压测平台重建（沿用现有 JMeter 链路）、安全渗透测试（采购专业服务）、生产环境监控（shift-right 闭环为 L4 远期目标）。

## 成功标准（验收）

| 指标 | 基线（P0 测得） | 目标（M12） |
| --- | --- | --- |
| 核心流程冒烟耗时 | TBD | < 5 分钟 |
| 全量回归墙钟时间 | TBD | < 30 分钟 |
| 测试资产线上化率 | ~0% | 100% |
| Top 20 机型主链路一键回归 | 不支持 | 支持 |
| flaky 率 | 不可度量 | 可度量且 < 5% |
| 试点业务线 UI 脚本维护工时 | TBD | 下降 > 50% |
| AI 生成用例 | 0 | 有占比度量 + 100% 人工审核入库 |

## 备选方案及不采用理由

1. **纯商业采购（如直接买 mabl/Functionize 全家桶）**：见效快但供应商锁定严重（迁移 100 用例约 2–4 周）、国内机型覆盖弱、敏感数据合规风险。不采用为主干，可作为局部能力补充。
2. **纯自研平台**：可控性最高，但 6–12 个月内无法达到可用状态，且重复造轮子（MeterSphere/Sonic 已覆盖 80% 需求）。不采用。
3. **维持现状**：回归成本持续线性增长，不采用。
